# Investigation: total system lockup on UGREEN NAS with `led-ugreen`

**Status:** open, evidence collection in progress
**Hardware under test:** UGREEN DXP6800 Pro
**OS:** Unraid 7.4.0-beta.2 (kernel `6.18.47-Unraid`)
**Last known good:** Unraid 7.4.0-beta.1 (kernel `6.18.44-Unraid`)

## Summary

With the UGREEN LED driver active, the machine loses network connectivity and then
becomes completely unresponsive. Recovery requires a physical power cycle. Removing
the driver makes the system stable immediately.

The popular framing of this problem - "the kernel module needs rebuilding for the new
kernel" - is **wrong**, and this document exists mostly to kill that idea with evidence
so nobody else wastes a weekend on it.

## What was ruled out

### 1. Missing or mismatched kernel module

The Unraid plugin downloaded `ugreen_leds-<build>-6.18.47-Unraid-1.txz`, containing
`lib/modules/6.18.47-Unraid/extra/led-ugreen.ko.xz`, built for the exact running
kernel. Its MD5 matches the publisher's `.md5` file. The module loads.

**A correct module for the running kernel is present. The module is not missing,
not stale, and not corrupt.**

### 2. An out-of-date userspace package

The plugin's final release (`2026.09.04`) is **byte-identical** to the previous
release (`2024.07.12`) - same MD5. The final maintenance action on the Unraid plugin
was a version bump plus a `max="7.4.0-beta.1"` cap in the `.plg`, preventing
installation on newer Unraid rather than fixing anything.

**Users on the "old" package are running the same code as the "current" one.**

### 3. A regression introduced in 6.18.47

Kernel went `6.18.44` -> `6.18.47`: three upstream stable point releases, which carry
backported fixes rather than subsystem rewrites.

More importantly, **the same class of lockup is reported on entirely different
distributions and older kernels**. Upstream issue #81 documents complete hardware
lockups on a DXP4800 Plus under Proxmox, using the userspace CLI with no kernel
module involved. A reporter there added `sleep 1` between LED commands, ran
"stable" for three months, and then locked up anyway. A third report followed.

**The defect predates 6.18.47 and is not Unraid-specific.** The kernel bump appears
to have changed timing enough to move the failure from "eventually" to "immediately",
which is a difference in probability, not in kind.

## Observed system state

SMBus controller and bus population on the affected machine:

```
i801_smbus 0000:00:1f.4: SPD Write Disable is set
i801_smbus 0000:00:1f.4: SMBus using PCI interrupt
spd5118 0-0050: DDR5 temperature sensor: vendor 0x06:0x32 revision 1.6
spd5118 0-0052: DDR5 temperature sensor: vendor 0x06:0x32 revision 1.6
```

Relevant facts:

- The LED microcontroller is at address `0x3a` on `i2c-0`, the i801 SMBus.
- `spd5118` (DDR5 SPD hub / temperature sensors) shares that bus at `0x50` and `0x52`.
- Platform firmware also polls DIMM temperatures over the same bus for thermal
  management.
- The kernel command line does **not** contain `acpi_enforce_resources=lax`.
- `i2c-i801` is operating in **interrupt mode**, not polling. `disable_features=0x10`
  is the documented switch to force polling.

## Load generated by the stock configuration

Default Unraid plugin settings:

```
LED_REFRESH_INTERVAL="0.5"
```

and the netdev LED trigger is configured with `tx`, `rx` and `link` at a 500 ms
interval.

On a 6-bay DXP6800 Pro this produces, per 500 ms window:

- 6 disk LEDs on the `oneshot` trigger, each `shot` causing two brightness changes
- 1 netdev LED updating on link/tx/rx activity

That is roughly **14 blocking SMBus transactions every 500 ms**, indefinitely.

## Driver behaviour under failure

From `kmod/led-ugreen.h`:

```c
#define UGREEN_LED_CHANGE_STATE_RETRY_COUNT   ( 5 )
```

From `kmod/led-ugreen.c`, `ugreen_led_change_state_robust()`:

- up to 5 attempts per state change
- `msleep(30)` between attempts
- `usleep_range(1500, 2500)` plus a status read after each write
- the entire sequence runs under a single `priv->mutex` shared by every LED
- brightness changes are dispatched through `brightness_set_blocking`, i.e. from
  workqueue context

A healthy transaction costs a few milliseconds. A failing one costs up to roughly
**140 ms of sleeping while holding the shared mutex**.

### Working hypothesis (NOT yet confirmed)

Once SMBus transactions begin failing, each LED update becomes ~140 ms of blocking
work on a shared mutex, while new LED work continues to arrive every 100-500 ms.
Work then arrives faster than it can drain, producing an unbounded backlog of
blocked workqueue items. This is a candidate explanation for the reported ordering
of symptoms - network connectivity dying first, total unresponsiveness following.

**This is a hypothesis. It has not been confirmed with a kernel trace, and no fix
should be written against it until it has been.** The alternative explanations -
a genuine SMBus controller wedge at the hardware level, or bus contention between
`led-ugreen`, `spd5118` and platform firmware - remain open and are not mutually
exclusive with the above.

Notably, the driver has **no failure ceiling**. It retries indefinitely, at full
rate, on a bus that may already be wedged. There is no path by which it gives up and
disables itself.

## Why no trace exists yet

Every public report of this bug loses its evidence at the moment the bug becomes
interesting: the machine hard-locks with the logs still in memory. Upstream issue #81
has been open since January with no trace attached, which is very likely why it has
gone nowhere.

## Evidence collection plan

**Phase 1 - capture.** netconsole from the affected machine to a UDP listener on a
separate host, so kernel output survives the lockup. Reproduce deliberately on an
expendable machine and capture the final messages.

**Phase 2 - mitigations to A/B**, neither requiring code changes:

1. `i2c_i801.disable_features=0x10` on the kernel command line, forcing SMBus
   polling instead of interrupt mode.
2. Raise `LED_REFRESH_INTERVAL` and reduce the netdev trigger to `link` only,
   removing the large majority of bus traffic.

**Phase 3 - driver fix**, directed by whatever Phase 1 shows. Candidate directions,
to be confirmed rather than assumed:

- a consecutive-failure ceiling after which the driver stops issuing transactions
- coalescing or rate-limiting LED updates so queued work cannot outrun the bus
- reconsidering unbounded retry-with-sleep while holding a shared mutex

## Upstream references

## Reproduction notes

Testing is being done on a dedicated spare machine. Deliberately hard-locking a NAS
that holds data you care about is a bad idea; do not reproduce this on a production
array.
